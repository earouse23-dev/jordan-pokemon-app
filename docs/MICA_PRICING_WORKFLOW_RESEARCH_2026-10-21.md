## What established workflows actually do

- [Card Ladder's published graded-card algorithm](https://cardladder.zendesk.com/hc/en-us/articles/41757251784215-Card-Ladder-Value-Algorithm-For-Graded-Cards-Without-a-Ladder-Profile) first resolves card, grade and grader, excludes flagged sellers and applies a recent-sales/outlier process before choosing a representative sale. It documents different handling for researcher-reviewed Ladder profiles and index adjustments for older evidence. These are vendor-described methods, not independently verified accuracy. We can reuse public statistical principles; we do not have its proprietary index or research team.
- Its [search guidance](https://cardladder.zendesk.com/hc/en-us/articles/12047786944663-12-Rules-for-Writing-Search-Queries) balances concise aliases with exclusions for other graders, grades, variants, lots, reprints and unrelated items. Broad retrieval and strict validation are separate jobs. A long eBay shopping URL does not prove the same query generates every internal valuation.
- [eBay Product Research](https://www.ebay.com/help/selling/selling-tools/product-research?id=4853) supplies precise seller research and actual accepted-offer amounts, unlike ordinary sold-search results. [PSA](https://www.psacard.com/cardvalue) recommends refining by identity and grade and examining recent auction activity. These are useful dealer verification workflows; access to their web UI does not establish a licensed bulk API for Mica.
- [TCGplayer](https://help.tcgplayer.com/hc/en-us/articles/213588017-TCGplayer-Market-Price) describes recent completed transactions and outlier handling rather than active asking prices. Its raw-product market number is not a PSA 10 comparable sale.
- [PriceCharting](https://www.pricecharting.com/page/methodology) describes multiple sale statistics, recency, automated junk/outlier checks and manual/user review. This supports separating a market estimate from one latest transaction, not claiming we can reproduce its undisclosed formula.

## Confirmed source gaps

1. **The headline is one comp.** `latestEbaySoldValuation` calls the existing exact-sold evaluator with `allowOlderSales: true` and `allowPriceOutliers: true`, then chooses the newest eligible eBay row. It explicitly reduces confidence to limited/stale. Although identity and transaction checks exist, this is not a robust recent-market estimator. A recently recorded unusual amount can dominate. Rows sharing a date are ordered by transaction key, which does not establish the within-day order of sales.
2. **Corrections are missing from incremental sync.** Current [PkmnPrices documentation](https://www.pkmnprices.com/docs/ebay-listings) adds `updated_since` separately from `since`: corrections do not advance ingestion time. It also states that null sale type can retain an accepted offer's asking amount, and deletion tombstones are unavailable. Mica reads ingestion deltas but not correction deltas. Old data should remain saved while explicit source corrections update affected records; immutable pricing forever would preserve known mistakes.
3. **The retained key is unsafe for corrections.** It combines sale ID, amount, currency and sale date. A corrected amount becomes a second record rather than replacing the first. The exact-sold evaluator rejects conflicting duplicate transactions, so simply adding the corrections request would still be insufficient. Preserve the provider row ID and marketplace transaction ID separately; upsert source revisions by stable identity before filtering/revaluation. Grade/printing moves must invalidate the former context too.
4. **The chart connects date-only transactions as a continuous price line.** `completedSaleHistory` supplies individual sales; `cardPriceHistoryWindow` sorts timestamps; `mountPriceChart` connects them with zero tension and no visible dots. Different prices at identical midnight timestamps produce vertical strokes in an arbitrary order. Applying curves alone would disguise the issue.

## Recommended implementation sequence

1. **Prove freshness and matching first.** Trace card 17262's bounded latest response through retained cache, exclusions, selected comp and chart. Record why each newer row is accepted/rejected. Repeat on Blastoise Unlimited versus Shadowless, Espeon CGC 8.5 editions, PSA 9/10, BGS label tiers and CGC Pristine/Gem Mint. If the source lacks a competitor's October sale, report that coverage gap; no estimator can recover an unseen transaction.
2. **Keep the efficient saved pipeline and add corrections.** Reuse its leases, daily reservations, cursor checkpoints and single published dashboard revision. Backfill once; on subsequent scheduled updates fetch new ingestion and correction deltas, replace affected rows and rebuild only affected derived results. Do not delete historical data after 24 hours or re-download years on navigation. Handle deletion/moved-row limitations with bounded reconciliation of affected contexts under the existing budget, not an unrestricted full-catalog scan. Share public market evidence across users while keeping ownership/costs private.
3. **Separate latest comp from estimated market value.** Keep the dated latest comp available, with amount certainty and exact context. Build the primary estimate from a calibrated recent matching sample using the existing evaluator/outlier helpers; compare median/recency-aware alternatives against labelled real examples before choosing thresholds. Known paid amounts should carry more evidential weight than unknown offer amounts. Sparse evidence must yield a range/limited estimate or unavailable result, with no raw-price substitution for a slab. Keep provider-native currencies and fee/shipping conventions explicit. TCGplayer can corroborate a truly matching raw context; do not average raw aggregates into slab prices.
4. **Redesign the chart's data presentation.** Show individual sales as dated points, retaining all records in details. For a readable primary trend, derive a deterministic daily representative (initial candidate: daily median with count/range) rather than joining arbitrary same-day prices. Label aggregation and any interpolated line. Preserve gaps/coverage and source dates; an empty day is not a zero sale. Match the selected date window, show freshness, use restrained grids and responsive dimensions, and keep points/tooltips usable on SE. Compute period change from the chosen representative series, not whichever same-day ID happens to sort first. Purchase-cost estimates belong to the approved portfolio fallback, not to a card's claimed sold-price history.
5. **Validate before replacing live pricing.** Run candidate and existing estimates against the same retained evidence without spending duplicate credits. Review representative real listing identities and exclusions; test same-day sales, accepted offers, corrected prices/grades, moved records, duplicate transactions, pagination, sparse/outlier data, FX and account switching. Verify one daily update, same-day reopen without provider calls, and atomic card/portfolio publication. Review matched-grade screenshots on desktop and SE/WebKit. Synthetic test counts alone cannot certify market accuracy.

The highest priority is freshness and trustworthy matching, then source-correction handling, then the headline estimator and chart presentation. A prettier line cannot compensate for incomplete or incorrectly attributed evidence. No new subscription is required for this proposed work; any demonstrated source-coverage shortfall remains an explicit limitation rather than an invented market value.
