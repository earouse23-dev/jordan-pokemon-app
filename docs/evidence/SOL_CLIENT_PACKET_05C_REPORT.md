## Effective request and quota contract

For the sold endpoint, the documented query parameter is **`limit`**, not `per_page`; it defaults to 20 and has max 20. The existing adapter and isolated guard's `limit=10&sort=date_desc&graded=true&variant=Holofoil&grader=PSA&grade=10` match that endpoint's parameter contract. A single page can contain **at most ten returned rows** under the documented limit; the OpenAPI notes that deduplication after page read may return fewer while `has_more` stays true. No cursor follow-up is authorized. Direct card detail is one credit; sold listings charge one per returned row. The intended upper reservation remains **1 + 10 = 11** across **two HTTP requests**. These are documented ceilings, not a measured charge. Post-response row-count validation is useful as a contract check but is not the budget control; the request limit and pre-transport reservation are. [Endpoint docs](https://www.pkmnprices.com/docs/ebay-listings), [OpenAPI](https://api.pkmnprices.com/openapi.json), [credit rules](https://www.pkmnprices.com/docs/rate-limits).

No guard parameter change is needed. The existing isolated guard's exact URLs, ordered count, retry/fallback rejection, and `redirect:"error"` remain appropriate; the future lookup needs the provider-facing set alias and a pre-request identity assertion. The public endpoint docs and OpenAPI do not specify an official per-response charge header. The local `lib/pkmnprices-readiness.js` and CLIENT-01 evidence use `x-credits-charged` as an observed/optional header; record it if present and numeric, otherwise report **unknown**, never zero. No paid probe was made to discover header behavior.
