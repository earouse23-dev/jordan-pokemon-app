## Request guard and identity results

Allowed simulated order is exactly `GET /v1/cards/20618?currency=usd`, then, only after the synthetic direct identity/printing gate succeeds, `GET /v1/cards/20618/listings/ebay?limit=10&sort=date_desc&graded=true&variant=1st+Edition+Holofoil&grader=PSA&grade=10`. The guard reserves 1 and then 10 simulated credits. It forces `redirect:"error"`; wrong host/ID, search URL, changed limit, cursor, retry, early/third request, and a redirect-follow option stop before fake transport. HTTP 302, 404 and 500 direct responses cannot unlock sales, retry or search. More than ten returned synthetic rows stop at the guard. Catalog drift stops before the first request. A mismatched or missing provider ID/name/number/total/set/language/first-edition USD variant stops after one reserved simulated credit, before sales. These checks exercise the actual API and adapter path where appropriate, with the guard intercepting global `fetch` only for the test and restoring it afterward.

The direct gate is deliberately stronger than the unchanged adapter's built-in `matchesPkmnPricesIdentity`: the adapter compares name, set and first number string but does not establish total, English language or detailed first-edition association. This additional candidate-specific gate is test code, not a production matching change. Its synthetic success says only that the future response shape **could** pass. If actual provider card detail does not expose one of those required facts, the experiment must stop or Astra must explicitly resolve the uncertainty first.

### R1: collector-corroborated suffix comparison

Before editing, a direct offline call to `saleMatchesCanonicalIdentity` returned `false` for synthetic direct card `20618` / `Clefable (1)` / `01` / `64`, lookup `Clefable (1)` / `01/64`, and title `Clefable Jungle 01/64 1st Edition Holofoil PSA 10`. The updated 05K executable expectations failed **2 of 10** before the fix: the three bare-name rows were still API-rejected (0 accepted instead of 3), and the focused suffix check returned false.

`lib/providers/pkmnprices.js` now disregards one **terminal numeric parenthetical in the name comparison only** when the requested collector number and total, the direct provider card number and total, and the suffix all agree. It requires the direct and requested names to agree, retains the base name words, requires a title set anchor and an independently present matching fraction or tagged collector number, and rejects conflicting or multiple title parentheticals. It leaves the original card name, lookup, title, IDs and returned evidence untouched. Missing number/total corroboration, a contradictory suffix, another parenthetical, or a meaningful base-name token keeps the strict name check. Existing fraction-conflict, title-ambiguity, language and set checks still apply. No direct-card matching or global catalog alias was changed.

After the fix, the same three **synthetic** bare-name sales at USD `100/120/140` pass the actual `api/sales.js` → adapter → `exactSoldValuation` path: **3 accepted, 3 contributors, ready, median USD 120, range USD 100–140**, matching the independent raw-row calculation and newest synthetic sold date. The original suffixed-title positive sample still passes. Focused negatives reject suffix `2` for collector `1`, conflicting provider number/total, missing requested total, missing sale number evidence (even when the sale repeats `(1)`), wrong fraction total, wrong sale `(2)`, multiple or nonnumeric name parentheticals, V/VMAX/ex/LV.X, regional and embedded-digit name distinctions, and wrong set. The prior mixed-row case still excludes unlimited/non-holo, wrong card/number/set, PSA 9 or qualifier, Japanese, EUR and shared-attribution evidence. The only changed comparison is the redundant name token; `saleMatchesLookup` still enforces printing, grade, qualifier, language and exact attribution before the canonical-title check, while the estimator still enforces native currency, dates, distinct transactions, outliers and minimum three contributors. The suffix cannot turn an unlimited/non-holo or otherwise invalid row into a contributor.
