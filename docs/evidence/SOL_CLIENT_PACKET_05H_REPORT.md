## Corrected source-to-normalized expectations

All positive shapes below are **constructed synthetic records**. The previously observed public Pikachu is reconstructed from retained CLIENT-05C observations, not refetched. The observed API record identifies its detailed variant with `variantId`. The [published database schema](https://github.com/tcgdex/cards-database/blob/master/interfaces.d.ts) describes `type`, `size`, optional `subtype`, `stamp`, `foil`, plural `languages`, and `thirdParty`; it does not itself establish the API's `variantId` field. Independent `variants` booleans do not establish combinations. An absent optional field is distinct from a present empty stamp list.

| Source case                                                                                           | Expected printing / eligibility                                                                              |
| ----------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------ |
| Explicit `type:holo`, `size:standard`, `subtype:unlimited`, `stamp:[]`                                | Holofoil, unlimited, no additional stamp, exact if language/card facts agree; stable namespaced source ID.   |
| `stamp:['1st-edition']`, standard holo, subtype absent                                                | First edition, exact if supported and nonconflicting.                                                        |
| `stamp:['staff']` or `['pre-release']`; standard holo; explicit unlimited subtype                     | Qualifier retained; distinct from unstamped counterpart.                                                     |
| Missing subtype without first-edition stamp; or missing stamp                                         | Corresponding edition/promo remains unknown; needs review, even when `firstEdition:false` or `wPromo:false`. |
| Duplicate source IDs or conflicting detailed/boolean facts                                            | Review needed; never pick an arbitrary exact printing.                                                       |
| Reordered source records; two holo variants with differing subtype/stamp                              | IDs and selection remain stable; no finish-only fallback.                                                    |
| Jumbo, unsupported foil/stamp/subtype, `languages` excluding the selected language, malformed details | Review needed; never ordinary exact standard valuation.                                                      |
| No usable detailed records                                                                            | Preserve the existing independent-flag fallback and legacy raw/sealed facts; do not synthesize combinations. |
| Observed Pikachu `2023sv-6`, detailed `jr7oetx1mqug9`, holo/standard, no subtype/stamp                | Preserve source variant reference and holo/standard; edition/promo unknown, no exact estimate.               |

Detailed record IDs are independent of response order, including two records with the same finish. Duplicate or malformed IDs and contradictions with explicit negative card flags disable exactness. Complete detailed records also require card ID, name, set, collector number and selected language. Unsupported treatment, stamp or subtype cannot be promoted by generic variant defaults. In the actual detail path, source-detailed option facts and review status take priority over a conflicting stale item field before the unchanged estimator runs.

Selection preserves a missing detailed source ID as an `Unavailable printing` review-needed option even when all detailed records disappear, only independent flags remain, or malformed details replace them. It does not select a printing by finish, label, or position in those cases. Existing legacy selected IDs and database variant UUIDs are not rewritten: hydration favors a saved UUID, then the namespaced source reference retained in the identity snapshot. The source ID also survives an owner-scoped saved identity snapshot as metadata. No migration/backfill or automatic inventory mutation was added. Existing raw/sealed and non-detailed selections keep their prior fallback behavior; 05H does not introduce a cross-provider set alias.
