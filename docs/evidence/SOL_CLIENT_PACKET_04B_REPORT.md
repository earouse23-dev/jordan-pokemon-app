## Internal normalized contract

`internal/certificate-fixtures.js` is a Mica-owned **invented** adapter implementing `lookup({ grader, certificate, signal })`. Results are `match`, `not_found`, `unsupported` or `ambiguous`. A match carries an exact string certificate, grader, optional `identity` (`name`, `set`, `number`, `variant`, `finish`, `language`), optional exact grade/qualifier/subgrades/images, source and observation time, and optional `population` (`source`, `asOf`, `coverage`, `total`, grade counts, optional dated history). UI validation rejects missing required match fields and unsupported language. Absent optional facts display as unavailable, never as zero or inferred facts. Errors represent offline, entitlement, rate limit, unavailable and malformed responses; retries retain input. Abort and generation/owner checks discard delayed results after edits, cancellation, close or account change.

**Assumptions:** This is an internal response shape, not a GemRate wire schema. PSA/BGS sample records, English/Japanese/German identity, half grades, subgrades, image and population values are synthetic. The sample image is a local drawing with explicit sample text. The BGS dated history is an invented fixture used only to exercise conditional history rendering. No official provenance or provider image rights are inferred. A future server adapter must normalize authorized provider responses to this contract and validate rights before returning images or storing facts.

The fixture owner is `certificate-fixture-owner`. Its saves and edits exist only in the internal build's in-memory `state.items`; normalized observations live in an internal `Map` keyed by physical-copy UID. No fixture fact is sent to Supabase or survives reload. The fixture save uses the original Add card form's validation, queue callback and retry identity with an in-memory adapter. Only coherent fixture matches attach a certificate; unresolved records do not replace an active association or escalate provenance. A separately entered user cert remains a user claim. No new database persistence path or migration exists. CLIENT-03's [isolated real database proof](SOL_CLIENT_PACKET_03_REPORT.md) still applies to the unchanged production create/update boundary, but CLIENT-04B did **not** rerun that database or prove a real-provider-to-database flow.
