## Effective entitlement and failure boundary

The original target had no development team or custom entitlements setting. Its effective simulator settings enabled signing and Xcode base-entitlement injection while requiring no provisioning profile. Xcode generated `App.app-Simulated.xcent` with `application-identifier = FAKETEAMID.dev.mica.client07.local`. The ordinary signed bundle's signature is local ad hoc, with `TeamIdentifier=not set`. `codesign -d --entitlements` did not print a separate blob, but the executable has a `__TEXT,__entitlements` section containing Xcode's generated simulator identifier. The ordinary unsigned executable lacked that section and displayed the existing fail-closed secure-start state. Apple's [Keychain missing-entitlement reference](https://developer.apple.com/documentation/security/errsecmissingentitlement), [default Keychain access-group guidance](https://developer.apple.com/documentation/security/sharing-access-to-keychain-items-among-a-collection-of-apps), [Xcode build-setting reference](https://developer.apple.com/documentation/xcode/build-settings-reference) and [QA1710](https://developer.apple.com/library/archive/qa/qa1710/) support inspecting effective generated identifiers rather than guessing a client team value.

The earlier manually crafted `LOCALDEV` simulator signature was rejected at CoreSimulator spawn with `error=163: Security policy issue`; the prior unsigned 07B Swift probe saw OSStatus `-34018` after a valid origin/key check. These are distinct observations. The current normal Xcode-managed signed simulator build launches and its Swift Keychain calls succeed, so **an Apple signing identity is not a remaining simulator-storage prerequisite**. It remains relevant to the separately authorized physical-device/distribution path. No fake prefix was added to repository settings, no shared Keychain group was added, and no fallback to Preferences or relaxed origin/key guard was introduced.

The storage probe used only `mica.auth-return` from the existing four-key allowlist and a nonsecret canary. The first process confirmed missing → set → exact get. After `simctl terminate` and `simctl launch` with a new process ID, it confirmed exact get → remove → missing get; `mica.07c-disallowed` rejected with the app's generic unsupported-storage error. The canary was cleared before restoring the clean app. The separate draft probe used only a synthetic UUID owner and cleared its test metadata. Screenshot hashes and precise command outcomes are in the [command record](sol-client-07c/commands-and-results.md). The screenshots prove observed UI diagnostics in a real simulator, while the diagnostic copy means they do not by themselves prove a backend session or production account flow.
