# Mica Step 1 completion appendix

**Evidence date:** 2026-08-31

This appendix is the detailed inventory required by Step 1 of
`docs/MICA_SOFTWARE_ROADMAP.md`. It supersedes older route, data-flow, security,
QA, and performance counts when those documents disagree with this snapshot.
It is an audit artifact, not a claim that unverified behavior works.

## Evidence labels

- **Live-read-only:** observed through a public production request or connected
  service metadata without opening private records.
- **Source-verified:** traced through the current repository and tests; no real
  account or persistence claim is implied.
- **Local-browser:** rendered from a configuration-neutral build. Authenticated
  markup is synthetic and contains no production account data.
- **Unverified:** the required account, device, credential, provider entitlement,
  or safe environment was unavailable. This is a valid Step 1 audit result and
  becomes an implementation or release dependency in the later roadmap step
  named in the registers below.

## Data-flow map

### Authentication and private portfolio

1. The browser creates a Supabase client from the two public configuration values.
2. Supabase Auth returns a session/JWT; unauthenticated users remain at `#authGate`.
3. `applySession()` clears prior in-memory owner state before loading profile,
   collection, watchlist, and valuation history.
4. Browser reads/writes go to the Data API with the user JWT. Owner-scoped RLS
   and invoker RPCs are the trusted authorization boundary.
5. Hydrated rows feed portfolio domain functions and UI renderers. Errors are
   shown through view state or toast; dashboard stale-state handling is incomplete.

### Catalog, pricing, and market evidence

1. A search or owned identity is normalized in the browser.
2. Catalog and set requests go through public Vercel Functions to the internal
   catalog or TCGdex.
3. Current price requests fan through `/api/cards`: PkmnPrices first when
   configured, then JustTCG and public TCGdex fallbacks.
4. Offers, sold evidence, graded/history features, and sealed data require the
   paid provider entitlement that production does not have.
5. Responses are normalized before rendering; unsupported, missing, stale, and
   zero values remain distinct.

### Identification and grading

1. The browser captures and locally prepares bounded card images.
2. `/api/vision` authenticates the user and claims a durable usage allowance.
3. Identity or grading requests go through Vercel AI Gateway. Precision grading
   may fan the same images to several provider families and may resend them for
   registered-reference comparison; `store:false` is set on model requests.
4. Model output is treated as untrusted structured input, normalized, checked
   for agreement/abstention, and presented for human confirmation.
5. Measurements/reports persist through owner RPCs. Normal images are not stored;
   consented research images upload directly from the authenticated browser to
   the private `grading-research` bucket.

### Account and research deletion

1. The user types the account email and sends a bearer-authenticated DELETE.
2. The server verifies bearer identity and email, then calls the training
   withdrawal service.
3. It inventories/removes owner paths in the three grading buckets, revokes
   sessions, and deletes the Auth user; cascades remove owner rows.
4. Research withdrawal also uses a deletion queue/worker. Production lacks the
   withdrawal RPC used by current account code and the lease used to recover a
   worker interrupted after claim, so the current source/live-schema pair is blocked.
